# Contract state migration boundary

The shared testnet city currently supports **state-preserving code upgrades**. The `upgrade_testnet` rehearsal imports the live state into a sandbox, deploys a candidate, compares every storage key and known view, including a real owner account, its cars and active session, then redeploys the previous WASM and checks the same state again. It does not change serialized state. Do not use that rehearsal as approval for a schema change.

The ordinary `testnet:code:plan` and `testnet:code:upgrade` commands now run both stored-layout fixture tests before reading the release WASM or contacting testnet. The example itself enforces this check, including when called directly. `npm run contract:layout:check` runs the same local guard without a network call. If a fixture changes, use the separate migration path below; changing an expected hash to make this guard pass is not a migration rehearsal.

## Stored layout today

`Contract` is stored under NEAR's contract-state key as Borsh. Its root contains roles, `GameConfig`, counters, treasury and inspector limits, plus `LookupMap` handles. The maps store `AccountState`, `Car`, `Plot`, `NPCSite` and `ParkingSession` values separately. `space_sessions` and the plot/NPC ID maps also live in storage. The `stored_value_layout_fixtures` contract test pins representative Borsh hashes for the root, config and each main value type. `stored_enum_variant_tags` additionally pins every current persisted enum variant's Borsh tag and the payload layout of Meter and ColorOnly rules. A changed fixture is a review signal, **not** permission to replace its expected hash and deploy.

The map prefixes are part of the persisted format: accounts `a`, cars `c`, plots `p`, plot IDs `i`, NPC sites `n`, NPC IDs `j`, sessions `s`, and occupied spaces `o`. `LookupMap` does not enumerate stored keys. Cars and sessions have monotonic IDs, and plots/NPC sites have ID indexes; accounts have no complete on-chain index. An eager account-value migration cannot safely claim to have found every player from contract state alone.

## Required path for a future schema change

1. Freeze the old source revision, WASM hash, exact Borsh definitions, storage prefixes and layout fixtures. Specify every changed root/value field and enum variant, including defaults for old records and new storage costs.
2. Write a separate migration candidate that reads the **old** root representation from storage before writing a new root. NEAR SDK 5.30.1 documents `#[init(ignore_state)]` as skipping the initialized-state check and `env::state_read`/`state_write` as Borsh reads/writes of the root key. A migration entry point using that attribute therefore needs an explicit contract-account/admin authorization check and an old-state/version guard; an unrestricted initializer would be unsafe. Keep the old type definitions in the migration binary until the conversion is complete.
3. For changed map values, build an explicit conversion plan. Enumerate cars/sessions by their stored ID counters and plots/NPC sites by their ID indexes, while accounting for gaps. For accounts, choose and test a lazy, version-aware read/write path or add a proven complete index **before** changing account values. Do not interpret old account bytes as the new struct. Keep old and new prefixes distinct if both representations coexist, and reconcile storage reserves and coin totals.
4. Rehearse on an exact imported snapshot of the target city. Check every raw storage key, migrated record count, balances, plot ownership, parked sessions, media approvals and public views. Exercise reads and writes of records in each old-state variant and a restart after partial or interrupted work. Reject any unaccounted record or changed economic total.
5. Decide the rollback boundary **before** deployment. Once migrated bytes are written, redeploying old WASM alone may fail to deserialize them. Either demonstrate a tested reverse migration on the imported snapshot or treat the migration as forward-only with a separately tested recovery binary and a stopped-traffic window. Keep the old code and state snapshot protected outside the repository.
6. Only after the rehearsal passes, run the live migration with an immutable source/code record, operator sign-off and post-migration readback. Record the state root, code hash, transaction, counts and conservation checks. Resume gameplay and the event indexer only after verification.

## Isolated root migration rehearsal

`npm run contract:migration:rehearse` builds a disposable forward and reverse probe, imports the exact shared testnet contract code and all 181 storage keys into a local NEAR sandbox, and changes only the Borsh root. The forward probe appends a `u32` schema marker (`2`) after the complete frozen V1 root. Its `LookupMap` handles preserve their prefixes and every map value remains opaque and untouched. The reverse probe removes that marker, after which the previous WASM is restored. Neither probe is deployed to testnet.

The [public rehearsal record](../deployments/testnet-root-migration-rehearsal.json) includes old, forward and reverse code hashes, the imported live-state hash, and separate hashes for the active-session fixture before/after rollback and during migration. The run verified exact imported bytes, representative live views, rejection of an outsider's migration and a second migration, unchanged non-root storage, exact restored state bytes, and working old views after restoring the old code. It also decoded and reserialized every stored account, car, plot, NPC site, index and occupancy record using the current V1 types; checked ownership and active-session links, index coverage and storage reserves; and compared account plus treasury coin totals before and after migration. The live snapshot had no active parking session, so **before** deploying the forward probe the rehearsal registered a sandbox-only driver and parked on an unowned Free plot. The forward migration preserved the session's exact stored bytes, terms and occupied-space link; the reverse restored all fixture bytes. The restored old code returned the same session view, then collected it and cleared both links. The sandbox-only registration increased the fixture's total coins by its normal starting grant; conservation was checked between the active fixture and migrated state, not against the smaller live snapshot. The forward and reverse methods require a call from the contract account; the rehearsal makes those calls with the imported contract account. The pinned near-sdk 5.30.1 [`#[init(ignore_state)]` documentation](https://docs.rs/near-sdk/5.30.1/near_sdk/attr.near.html) and [`env::state_read` documentation](https://docs.rs/near-sdk/5.30.1/near_sdk/env/fn.state_read.html) were checked before using this entry-point pattern.

This proves the mechanics and rollback boundary for a root-only marker on the current city and that the current code decodes every record in this particular live snapshot. The active session is a sandbox fixture, not a live player's parked car. The probe has no gameplay methods during its temporary deployment, so the rehearsal assumes stopped traffic. It does not convert account, car, plot, NPC or session values; it does not test partial record migration or a production schema change. The release gate remains open for any actual changed layout, complete value-conversion plan and candidate-specific rehearsal. The current layout fixtures cover every current enum variant but only representative composite values; the live audit cannot prove decoding of variants absent from this snapshot.
