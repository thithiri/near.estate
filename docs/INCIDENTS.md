# Incident procedures

These procedures apply to the testnet invite beta. Run commands from the release checkout with the same Compose files and protected environment used for that deployment. Record the incident time, contract ID, release commit, affected plot/job IDs, and each transaction hash in the operator log. Never paste keys, Basic-auth passwords, cookies, or private artwork into that log.

The contract roles and current pause state are readable through `get_roles` and `is_paused`; the deployment ID and expected code hash are in [`deployments/testnet.json`](../deployments/testnet.json). The API and event worker share `/data/estate.sqlite`. Before changing data or code, create and verify a [state backup](RECOVERY.md).

## Moderation and urgent revocation

1. Open `/api/moderation` over HTTPS with the protected reviewer account. Check the current owner, plot, building type, level, layout revision, pending hash, and nearby buildings shown in the preview. Inspect the full sprite and logo/billboard placement, including links. A thumbnail alone is insufficient.
2. For paid art, first approve or reject each **private candidate** using the content, style, and placement checks. Only approved candidates become selectable by the owner. For the selected facade, or a logo/billboard, submit the corresponding exact approval or rejection form. A rejected item stays private; record a reason. If the page reports `awaiting_finality`, wait and reopen it before retrying.
3. If active content must be withdrawn, use its **Revoke active design** or **Revoke active logo/billboard** form. The service rereads the exact active hash and revision before signing. Confirm the finalized chain plot no longer marks that asset eligible, then reload the street: the facade should return to its preset, a logo to initials, or a billboard should disappear.
4. Check the indexer and API logs for the decision, and record the transaction hash and reason. Once-public image bytes remain hash-addressable in the API even after chain revocation; revocation removes game display permission, not the historical file. Escalate any legal request to remove hosted bytes separately because deleting a referenced file breaks the current backup and history guarantees.

If the review page cannot read the current plot or media bytes, leave the item pending. Do not approve from an old screenshot or bypass the exact-reference check. If the moderator key is suspected compromised, stop API moderation signing and follow **Key loss or rotation** below.

If `/api/assets/:hash` or `/api/manifests/:hash` returns `ASSET_CORRUPT`, preserve the affected file/database and logs, stop new approvals for that asset, and restore the exact hash-matching bytes from a verified backup. The API will not send corrupt bytes with a long-lived cache header. Check the same URL again after recovery before resuming review.

## Suspend or resume paid image generation

1. Set `IMAGE_GENERATION_ENABLED=false` in the protected API runtime environment, then recreate the API service with the same release image and volume. Confirm `/api/health` is healthy and the owner interface no longer offers paid prompting. Curated presets, existing parking, and approved art remain available.
2. Inspect `paid_generation_jobs` and `paid_generation_attempts` in a read-only copy or stopped-service backup. A call recorded as `started` when the process was interrupted can become `uncertain` after its lease expires. An uncertain attempt keeps its conservative charge and is never automatically resent. Preserve its `client_request_id`, provider request ID if present, and outcome evidence.
3. With the API **stopped** and the original protected paid-generation environment available, first run `npm run paid:reconcile -w @estate/api -- --plan <data-dir> <job-id> <client-request-id>`. Compare the returned attempt number, provider request ID and conservative charge with the provider's account-side record. Only a confirmed **nonreceipt and noncharge** justifies `confirmed_not_received`; a confirmed charge uses `confirmed_charged`. An unknown outcome stays held.
4. After a verified backup, run `ESTATE_RECONCILE_OFFLINE=true IMAGE_GENERATION_ENABLED=true npm run paid:reconcile -w @estate/api -- --apply <data-dir> <job-id> <client-request-id> <confirmed_not_received|confirmed_charged> '<provider-evidence-note>'`. The command uses the normal protected paid-generation settings, records a 4–500-character note, changes the held attempt once, and prints the resulting job/charge state. The offline flag is an explicit operator acknowledgement; the command cannot detect another process writing the same volume. Do not edit SQLite rows by hand or retry the same prompt as a new request to clear it.
5. Resume only after checking the budget, reviewer capacity, and incident cause. Restore the original protected configuration, including invites, model, per-call ceiling, daily budget, timeout, and safety secret; set `IMAGE_GENERATION_ENABLED=true` and recreate the API. Confirm the API starts with the moderator signer and reviewer credentials present.

## RPC or event-source outage

1. Check `docker compose --profile indexer -f infra/compose.yaml logs --tail=100 indexer`, the API health route, and `GET /api/stats/economy`. The stats response's last indexed height and timestamp show how stale the read-only totals are. The API can serve gameplay views while the event worker retries, but old statistics must be treated as incomplete.
2. Check whether the failure is recent-block Neardata, account-history/archival FastNear, or the chain RPC. Verify the configured provider URL and protected `ESTATE_FASTNEAR_API_KEY` outside the repository. Correct only the affected environment value and restart the worker. Leave its SQLite cursor intact; it commits events and cursor together and retries a failed height.
3. Watch the worker log for a new `recent_blocks` or `sparse_history` JSON pass. Compare the new cursor to the pre-incident value, verify the contract ID and block linkage, then check stats freshness. If aggregates are suspect, stop the worker, preserve a backup, and run `npm run index:rebuild -w @estate/worker` against the same data directory and contract settings before restarting it.

Run only one indexer writer against a volume. Do not reset the cursor, change `INDEXER_START_HEIGHT` on a populated database, or switch to a different contract to make the worker start. If an archival provider cannot validate the saved anchor, keep the worker stopped and investigate the source or chain reorganization rather than force-advancing it.

## Key loss or rotation

The admin, moderator, and inspector are separate testnet account IDs fixed at contract initialization. Rotating a credential **within the same account** is possible; changing a role account ID requires a separately rehearsed contract upgrade or migration. The API receives only the moderator credential, the inspector process only its inspect credential, and the deployer full-access key stays outside both containers.

1. If a credential may be exposed, stop the process that holds it. For a moderator incident, disable the moderation override and paid generation before restarting the API; paid generation refuses to start without moderation. For inspector, stop the inspector profile. If the deployer key is exposed, also pause new contract economic actions with the admin account once control is recovered; existing settlement remains available.
2. Using a trusted NEAR account-management method outside this repository, add a replacement key to the **same** role account with only the methods and allowance that role needs. Verify the key is visible on-chain before removing the old one. Keep the credential file outside the checkout and make it readable only to the intended service account.
3. Revoke the old access key on-chain, then verify its absence. Update `MODERATOR_KEY_HOST_FILE` or `INSPECTOR_KEY_HOST_FILE` in the protected deployment environment and recreate only the affected service. The JSON `account_id` must match its configured role ID; startup rejects a mismatch.
4. Verify API health or a single bounded inspector pass, then verify a controlled role action and its finalized result when one is available. Record the old/new public keys, transaction hashes, and exact revocation height. Do not record private key material.

Browser gameplay keys belong to individual players. Their normal disconnect path asks the wallet to revoke the exact key before signing out. A copied or lost browser key must be revoked through that player's wallet; the operator cannot revoke a player's account key. If an account cannot revoke promptly, the admin can pause new economic actions while the player recovers access.

The artwork API separately binds its cookie session to the key used for wallet sign-in. Once that access key is absent at finalized chain state, the next private artwork request deletes the session and requires sign-in again. An RPC outage leaves the session intact but returns a temporary error. Existing keyless artwork sessions are cleared automatically on the schema update.

## Contract code rollback or state migration

The [tower-floor upgrade record](../deployments/testnet-floor-upgrade.json) and [initialization-guard upgrade record](../deployments/testnet-code-upgrade-007f67a531c87671f57a96660b4a61f3b7fca6a60681944c5b8227eaf0549c59.json) prove two **state-preserving** code replacements: the old WASM was kept in protected storage, a sandbox import kept every state key/value, and the live procedure compared code, state hash, roles, and city counts. The current `testnet:code:plan` and `testnet:code:upgrade` commands give each candidate code hash its own public record and compare the current tower views. The plan checks the new tower-floor batch and all ten street-side views after upgrading the imported city, then restores old code in that sandbox and rechecks state, tower views, roles and city counts. A failed live post-upgrade check leaves `recovery_required` in the public record until rollback verification succeeds; `rolled_back` means the original code and state were checked. These commands do not handle changes to serialized state.

1. Before a future code change, take and verify an API/indexer/artwork backup, preserve the live old WASM outside the repository, read the current live code hash and roles, and record the state hash. Pause new economic actions through `set_paused(true)` if the change can affect parking; collection and expiry settlement remain available under the current contract.
2. Import that exact state into a sandbox, deploy the candidate binary there, exercise the changed methods, and compare the complete key/value state and economic invariants. Prepare an upgrade tool for that candidate which verifies the exact old/new code hashes, records a public prepared recovery record, waits for finality, checks roles, counts and state, and can redeploy the saved old code if verification fails before any new-format writes.
3. Apply only after the rehearsal and recovery tool pass. If verification fails, keep admission paused, inspect the live hash and state, and restore old code only when its serializer still reads the current state. Recheck settlement and balances before unpausing. Restore API/indexer storage only for an off-chain data failure; it cannot roll back on-chain transactions.

**No general state-schema migration path is implemented.** A release that changes serialized contract state must include an explicit migration method, rehearsal using a copy of current live state, a compatibility/rollback boundary, and a fresh runbook before deployment. If new code has written a state format the old code cannot read, redeploying the old WASM alone is unsafe. This remains an invite-beta release gate.

## Service recovery and evidence

For `API_UNAVAILABLE`, check the API container health and recent logs, then query `/api/health` through Caddy. If the container is restarting, preserve its logs and verify that the shared SQLite volume is mounted and writable before restarting it. The monitor's separate database alert distinguishes an API process outage from inaccessible shared storage. Confirm the API alert resolves only after the service responds again; an external HTTPS check is still needed to confirm the public route.

For lost SQLite or image files, follow [RECOVERY.md](RECOVERY.md), which restores to a fresh volume and verifies hashes, cursor, and replay. After any incident, verify API health, the rendered street and approved media, the worker's advancing finalized cursor, and one role-specific path affected by the incident. Keep the pre-incident volume, backup, and logs until those checks pass. Update [DECISIONS.md](DECISIONS.md) with any changed trust boundary or operational rule.
