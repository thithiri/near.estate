## HTTP API

The API serves the game through the same origin at `/api/*` (Caddy removes the prefix before proxying). `APP_ORIGIN` must be the exact browser origin, including scheme and port. Unsafe requests require a matching `Origin` header. Errors use `{ "code": "MACHINE_CODE", "message": "Readable explanation" }`. Successful sign-in, upload and design-job responses use `Cache-Control: no-store`.

When connected to a contract, the API rechecks `city_version` after a 30-second cache interval. A changed version returns `CITY_VERSION_CHANGED` (503) on all routes, including health and impression intake, until the service restarts with the matching seed. An unavailable version read returns `CITY_VERSION_UNAVAILABLE` (503) and is retried on the next request. `/city` uses `Cache-Control: no-store`. This bounds the stale-seed window during city migration without changing the startup version check.

Artwork sessions are bound to the wallet public key that signed the challenge. Each protected artwork request rechecks that key at finalized chain state. A revoked key deletes its session and returns `KEY_REVOKED` (401); an RPC lookup failure returns `CHAIN_UNAVAILABLE` (503) and retains the session for retry. Public approved assets remain readable without a wallet. When an existing SQLite database gains the key-bound session column, old sessions without a stored key are deleted, so those users sign in again.

Content-addressed PNG and approved manifest reads recompute the SHA-256 hash before serving bytes under an immutable URL. A missing file returns 404; a file or manifest that no longer matches its address returns `ASSET_CORRUPT` (503) with `Cache-Control: no-store`. A corrected file or database record can then be served normally without changing the public URL.

Impressions are client-reported estimates. The street reports only a fully visible, loaded, approved logo or billboard after one continuous visible second, then flushes every ten seconds. Each event has a stable UUID for retries; the API stores it once, counts at most one impression per anonymous session, plot and minute, and credits at most 60 seconds of dwell for that group. Events may be at most five minutes old or 30 seconds ahead of server time. A session can store at most 60 new events per rolling minute and 5,000 per UTC day. The API stores the session token only as a hash. Expired raw session and event rows are cleared on the next new session or the startup/six-hour retention sweep; daily totals remain. These records never mint coins or prove billable ad delivery. The browser keeps unsent events locally for retry, while the API uses its persistent SQLite volume.

The local `/stats/economy` response now adds seven-day and full-indexed-history issued, known-spent, net-change and spend-to-issue fields. These are event-flow measures, not a verified supply balance. Its `heartBonus` issued amount counts separate `visit_bonus_paid` events; the coin audit includes the same events in the outstanding-supply reconciliation. Older event amounts remain explicitly unpriced. `/stats/plots/:id` adds known owner meter/ticket income, treasury allocation, legal/illegal park traffic and counts of old settlements whose recipient split cannot be attributed. The owner panel labels those unknown amounts as incomplete history. The separate read-only `npm run coin:audit -- /path/to/indexer.sqlite` reconciles historical config values and compares total coin flow to all registered balances plus treasury at one finalized indexed block.

For a city migration freeze, set `IMPRESSION_INTAKE_ENABLED=false` and recreate the API service before taking the final statistics snapshot. Both impression POST routes then return `IMPRESSION_INTAKE_PAUSED` without adding sessions or events, and the browser discards queued views. Before starting the version-2 API, apply and verify the reviewed deed-history move and set `CITY_DEED_CUTOVER_AT_MS` to its exact cutover time in Unix milliseconds. Version-2 API startup refuses a missing or inconsistent move, indexer cursor, workflow relocation or deed cutoff. Keep intake disabled through city unpause verification. Then restart with `IMPRESSION_INTAKE_ENABLED=true` and `IMPRESSION_ACCEPT_AFTER_MS` set to the release record's `reopenedAtMs`, which must be no earlier than the deed cutoff. The API rejects an event if its visible interval began before that time (`observedAt - msVisible < acceptAfterMs`); the browser drops those queued views and retries only newer ones. Both cutoff defaults are zero for ordinary version-1 operation. These controls affect ad estimates only, not coins or parking.

Uploading does not publish artwork. The owner prepares a private proposal from that immutable upload, sends `propose_media` with the wallet and confirms the exact on-chain pending record. The moderator then approves or rejects that exact revision. The API rechecks current on-chain ownership and the building layout revision after image processing so a plot sale or layout change during upload cannot attach the asset to stale state. It stores only a hash of the session token in SQLite. Wallet sign-in and media submission have not been exercised through both named browser wallets.

Mock design jobs composite the curated facades with three colour/shape combinations and create distinct immutable sprites, thumbnails and manifests. A versioned prompt specification records the paid level envelope, selected silhouette, palette, optional theme and up to two material hints, owner description, and eligible approved facade reference. Owners can turn off the prior-art reference to start a fresh design. Paid recolouring sends the current approved facade to the image edit endpoint; after an upgrade, the latest locally approved lower-level facade for the same owner, plot and type can supply that reference. Missing or corrupt reference art fails before any paid provider call. None of those words alter the three curated mock images. Only the originating account session can retrieve a pending job or its images. After every candidate has a content/style/placement decision, a completed paid job with one to three approved candidates is promoted to a design job with `mode: paid` and the same ID; it then uses `/generations/:id/select`, `/generations/:id/reconcile` and the existing moderator routes. The owner screen compares its choice to neighbours read from the current chain plot list. A job whose building type, level, layout or appearance revision no longer matches the plot cannot submit a new proposal. A selected job retains its chosen candidate across reloads; an exact chain pending reference is required before the API reports `submitted`.

Unchosen previews expire seven days after becoming ready; unselected choices from a selected job expire on the same schedule. An expired design job reports `status: expired` and no candidates. The selected choice remains available for proposal and review. Rejected paid candidate files are eligible for deletion seven days after moderator review. Unused media uploads expire seven days after upload; rejected media images expire once the upload and every linked rejection are at least seven days old. Their proposal status and reason remain in SQLite, and the owner must upload again before proposing that image. A six-hour cleanup removes old private files only when no live media, design or review record needs their hash. Once-published sprites, thumbnails and manifests remain available after withdrawal for history.

The moderator queue is enabled only when the API has a dedicated testnet moderator key file and review credentials. It renders the exact selected candidate and reads neighbouring plot metadata at review time. Approval and rejection call the contract using the full pending reference; the API then reads the finalized decision before changing job state. A successful approval publishes only the selected sprite/thumbnail and manifest. Revocation checks the active hash and current revision, signs the contract withdrawal, and records its reason. Once-published files remain available as immutable history, while the on-chain approved hash controls street display. The client verifies the fetched manifest's canonical SHA-256 hash and type/level before loading the sprite. Pending, unavailable or withdrawn art falls back to the curated preset.

`MediaKind` is `Logo` or `Billboard`. `MediaIdentity` contains `asset_hash` (lowercase SHA-256 hex) and `link` (an optional HTTPS URL). Media proposals also carry the owner, building type, level, layout revision and media revision. The street loads active media only when the corresponding `get_plot` eligibility boolean is true and the current facade has a placement rectangle. Otherwise the logo uses the building initials and the billboard remains hidden. A stored approval for an older building layout is not display permission. Contract approval records the moderator decision, while the API remains responsible for validating image bytes, placement and content. Once-public bytes remain addressable after revocation, but the chain flags remove them from the street.

## Contract events

Successful calls emit `EVENT_JSON:` logs with `standard: "near_estate"`, `version: "1.0.0"`, an event name, and a nonempty `data` array. The names and exact payload fields are defined in `packages/shared/src/events.ts`. Integer coin and yoctoNEAR amounts are decimal strings; bounded car and session IDs, slots, revisions and timestamps are JSON numbers. `parseGameEventLog` ignores ordinary logs and rejects malformed game events. Settlement payloads include gross, driver payout, recipient payout and forfeited amounts; the validator requires them to add up to gross. New local settlement events also separate `owner_payout`, `treasury_payout` and `owner_account`; these add to recipient payout. `ticket_reward_policy_set` records admin cap changes.

An indexer must process logs from finalized **successful** contract executions and deduplicate by receipt plus log position. The current schema validates individual event records. Finalized-source replay, durable cursor commits and aggregate rebuilds are Phase 7 work.

## Version-2 illustrated media

For version-2 illustrated plots, logo uploads remain available at every width and level. Billboard uploads and proposals currently require a Diner or Arcade design at level 3 or 4; unsupported requests return `NO_MEDIA_SURFACE` (409). The version-2 contract view reports `billboard_eligible: false` when a stored approval has no surface on the current design and level, including a billboard carried from the old city. The owner panel explains this state and does not offer reuse until a surface exists. The moderator's version-2 preview uses the catalog's hashed illustration and the shared placement geometry. A locally seeded version-2 facade job can be selected, reconciled and moderated only while its prompt, manifest and current plot agree on width, design, type and level. Owner requests and image processing pass local fake-provider checks behind a disabled paid-generation switch; actual provider calls and a named-wallet version-2 journey remain open before generated facades can be offered to players.
